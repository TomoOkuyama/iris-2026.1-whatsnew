# ベクトルサーチ改善 - ACORN-1アルゴリズム

## 概要

「カテゴリで絞り込みつつ、意味の近い文書を探したい」。RAGやレコメンドでよく出てくるこの要求に対応するのが、IRIS 2026.1のACORN-1アルゴリズムです。2025.1で追加されたHNSW（Hierarchical Navigable Small World）インデックスをベースに、WHERE句のフィルタ条件とベクトル類似度検索を分離せず一体で処理するのが、この新しいアルゴリズムの特徴です。しかも、既存のクエリやインデックスはそのまま利用できます。実際に動かして、挙動を確かめてみましょう。

> **注**: HNSWインデックス自体は2025.1で導入済みです。本ドキュメントでは2026.1の新機能であるACORN-1アルゴリズムに焦点を当てています。

---

### ACORN-1アルゴリズム（2026.1）

フィルタ付きベクトル検索の処理方式が、内部から作り替えられました。利点は、利用にあたって特別な対応が一切要らないことです。既存のHNSWインデックスに**自動的に適用**されるため、インデックスの作り直しも設定変更も必要ありません。いつものクエリのままで、検索が高速になります。

#### テーブルとベクトル列の定義

```sql
CREATE TABLE Demo.VectorDoc (
    ID INTEGER NOT NULL AUTO_INCREMENT,
    Title VARCHAR(200),
    Category VARCHAR(50),
    Embedding VECTOR(DOUBLE, 128),  -- 128次元の浮動小数点ベクトル
    PRIMARY KEY (ID)
)
```

ポイントは `VECTOR(DOUBLE, 128)` というベクトル列の型指定です。`DOUBLE` が要素の型（`DECIMAL` も指定可能）、`128` が次元数を示します。埋め込みモデルの出力次元に合わせて指定しておけば、この列に通常の列と同様にベクトルを格納できます。

#### HNSWインデックスの作成

ベクトル列に高速検索の機能を追加するのがHNSWインデックスです。次のSQL一行で作成できます:

```sql
CREATE INDEX HnswIdx ON Demo.VectorDoc (Embedding) AS %SQL.Index.HNSW
```

#### フィルタ付きベクトル検索（ACORN-1が自動適用）

```sql
-- アプリケーションコードでは ? パラメータでベクトルを渡す
SELECT TOP 5 ID, Title, Category,
    VECTOR_COSINE(Embedding, TO_VECTOR(?, DOUBLE, 128)) AS Score
FROM Demo.VectorDoc
WHERE Category = 'Technology'
ORDER BY Score DESC
```

見た目は通常のフィルタ付き類似度検索です。ただし、HNSWインデックスがある状態で2026.1がこれを実行すると、内部では自動的にACORN-1が適用されます。アプリケーション側で特別な記述をする必要がないのが、この機能の利点です。

> **クエリプランでの確認**: `$SYSTEM.SQL.Explain()` でACORN-1が適用されているとき、以下が表示されます:
> ```
> Info:
> This plan uses the ACORN-1 algorithm for vector search.
>
> Read index map Demo.VectorDoc.HnswIdx, looping on the 'VECTOR_COSINE' expression...
> ```
> デモの10万件規模でも同様に確認できます。

#### 従来方式との違い

| 項目 | 2025.3以前（検索後フィルタ） | 2026.1（ACORN-1） |
|------|----------------------|------------------|
| 処理の流れ | グラフ走査で候補を多めに取得 → フィルタ適用 | グラフ走査中にフィルタを同時評価 |
| フィルタ選択率が低い場合 | 大量の候補が除外され、結果不足の可能性 | グラフ接続性を利用して効率的に収集 |
| コードの変更 | — | **不要**（既存クエリのまま適用される） |

#### 実行コマンドと実測結果

実際に動かして確認します。デモクラス `Demo.Vector.VectorSearch` を**両バージョンで実行**し、同じ条件で測定した結果を比較してみましょう:

```objectscript
do ##class(Demo.Vector.VectorSearch).Run()
```

このRunは、100,000件（128次元、1,000カテゴリ、選択率約0.1%）のベクトルデータを生成したうえで、3パターンを各20回ずつ計測します。データの生成とHNSWインデックスの構築を含むため、**完了まで数分かかります**。実行中は他の作業を並行して進めておくとよいでしょう。

#### 実測結果（100,000件・1,000カテゴリ・選択率0.1%）

| パターン | 2025.1 | 2026.1 | 比率 |
|---------|--------|--------|------|
| A. インデックスなし・フィルタ付き | 0.054秒 | 0.213秒 | 下記考察参照 |
| **B. インデックスあり・フィルタなし** | 0.010秒 | **0.005秒** | **2.0倍高速** |
| **C. インデックスあり・フィルタ付き** | 0.044秒 | **0.044秒** | ほぼ同等 |

> Docker Desktop（Apple Silicon）での参考値。

#### 考察

**Bのフィルタなし検索が2倍高速化:** 今回の計測でもっとも明確に差が出た項目です。ACORN-1の本来の対象はフィルタ付き検索ですが、HNSWのグラフ走査そのものも2026.1で改良されているため、フィルタを使わないベクトル検索でも速度が向上しています。0.010秒から0.005秒となり、日常的な類似検索が、特別な対応をしなくても半分の時間で完了するようになります。

**Cのフィルタ付き検索が2025.1とほぼ同等な理由:** 意外に感じられるかもしれませんが、理由は単純です。ACORN-1の効果は**データ規模と選択率に強く依存**します。今回のデモ環境（100,000件・選択率0.1%で約100件がヒット）は、ACORN-1の効果が表れるにはまだ規模が小さいのです。明確な差が出るのは桁が変わってからで、数百万件以上かつ選択率0.01%以下、たとえば1億件のドキュメントを特定属性でふるい分けるような場面では、10倍以上の差が見込めます。

**A（インデックスなし）が2026.1で遅い理由:** 一見すると「新しいバージョンの方が遅い」のは不自然に思えますが、これは全件スキャンに固有の現象です。インデックスのない検索は内部のベクトル計算コストが支配的で、そこに2026.1の追加処理のオーバーヘッドが上乗せされてしまいます。逆に、インデックスを利用するBとCではこの関係が逆転しており、インデックスを利用してはじめて2026.1の改善効果が得られると言えます。

**重要:** 今回の規模ではACORN-1の速度差は数値として表れませんでしたが、価値はその先にあります。**コードも設定も変更せず自動で適用される**点が、実運用では重要になります。現時点ではデータ量が小さくても、将来データが大規模になった際に、追加の準備作業なしでACORN-1の効果を得られます。将来に向けた備えが、現在のクエリのまま整っているということです。

**A vs Cの比較（インデックス効果の確認）:** 同じ2026.1の中でインデックスなし（0.213秒）とACORN-1あり（0.044秒）を比較すると、その差は**約5倍**になります。HNSWインデックスを作成するだけで、フィルタ付きベクトル検索の性能がこれだけ変わります。インデックスの効果を端的に示す数値と言えます。

#### 活用シーン

- RAG（Retrieval Augmented Generation）の基盤として、「経理部の、今年度の規程だけ」から意味の近い文書を取得するなど、部署・カテゴリ・期間で絞ったセマンティック検索
- 商品レコメンデーションにおいて、「このカテゴリの、在庫がある商品の中で類似するもの」を即座に返すフィルタ付き類似度検索
- 数百万件を超える大規模ベクトルDBにおいて、精度を落とさずに属性で絞り込む用途。ACORN-1の効果がもっとも明確に表れる場面です
